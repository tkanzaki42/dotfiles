# Neovim更新の確認

更新内容を尋ねられたら、追加質問を待たずに、この環境に適用した場合の破壊的変更と対処の要否も報告する。調査だけの依頼ではインストールしない。更新を依頼された場合は、影響確認から更新後の検証まで進める。

## 更新対象と影響の判定

- `.config/nvim/init.lua`、`.config/nvim/lua/config/lazy.lua`、`.config/nvim/lazy-lock.json` と `nvim --version` を確認する。外部ツールの要件変更は `home.nix`、`flake.nix`、`flake.lock` とも照合する。バージョンや設定を過去の結果で固定しない。
- lazy.nvimが実際に選択する更新先を確認する。`version`、`branch`、`tag`、`commit`、`pin` を考慮し、単に `HEAD..origin/main` に差分があるだけで更新対象と判定しない。特に blink.cmp の `1.*` と toggleterm の `*` はmainの先端とは限らない。注釈付きタグはコミットへ解決して比較する。
- lockfileとインストール済みHEADが違う場合は区別する。取得済み履歴だけならその範囲を明記し、最新情報と断定しない。情報取得では環境のネットワーク・書き込み権限を守る。
- 現在のコミットから実際の更新先までの一次資料（Git差分、コミット本文、公式リリース・移行ガイド）を調べる。`!` や BREAKING CHANGE の有無だけで安全性を判定しない。対応Neovim、Lua API、設定キー、キーマップの動作、依存ツール、パーサーとクエリの互換性変更を、現在の設定と照合する。
- 上流に破壊的変更があるかと、現在の設定・利用言語に影響するかを分けて伝える。未使用と判断した場合は根拠も添える。実際の使用状況が分からないものは不明とする。
- 日本語で、実際の更新対象、主な変更、この環境への影響、必要な修正、未確認事項を簡潔に報告する。「破壊的変更の明記なし」を動作保証に置き換えない。

## 更新を依頼された場合

- 最初に作業ツリーと更新前lockfileを確認し、既存のユーザー変更を保持する。更新を承認済みなら一律の追加確認を挟まない。重大な機能廃止や判断が必要な移行があれば、影響と具体的な選択肢を示し、その判断に依存する操作を止める。
- lazy.nvimの設定に従って更新する。対象が限定されていれば範囲を守る。通常は `nvim --headless '+Lazy! update' +qa` を使い、非同期処理やビルドの完了とエラーまで確認する。dotfiles外のプラグインディレクトリへの書き込みなど、必要な権限は実行環境の承認手順で取得する。
- 更新後は新しいNeovimプロセスで通常のinitを読み込んで検証する。検証Luaは一時ディレクトリに置き、`nvim --headless '+luafile /absolute/path/check.lua'` の形で実行する。`nvim -l` は通常のinitを読み込まないため、この目的には使わない。
- 更新内容に応じて、起動エラー、プラグイン読み込み、LSP設定解決、使用言語のTreesitter解析とhighlight/injectionクエリ読み込み、SQLのFileTypeと補完初期化などを確認する。外部サービスへの接続は必要な範囲と権限に限る。モジュール読み込みと実際の補完・LSP通信・画面操作の確認は区別する。
- Treesitter更新時はビルドの `:TSUpdate` 結果も確認する。失敗した場合は原因と影響を調べ、成功扱いにしない。ロールバックが必要なら更新前のコミットとlockfileを使い、既存の変更を上書きしない。
- 最後に実際のlockfile差分、インストール結果、`git diff --check` と作業ツリーを確認する。予想と実際の更新対象が違えば訂正する。更新したプラグイン、実施した確認、残る確認を報告し、依頼がなければコミットしない。
